# Loom Loom!

System-agnostic TTRPG worldbuilding and session-management plugin for Obsidian. Tracks
characters, locations, factions, items, quests, events, and sessions as markdown notes with YAML
frontmatter, plus typed relationships between them, visualized through a custom timeline
and a custom layered graph view.

> **Doc upkeep is part of finishing a task, not a separate chore.** Whenever files are
> added, moved, renamed, or a feature is completed, update the file map below,
> `ROADMAP.md`, and (for design changes) `docs/ARCHITECTURE.md` in the same change.

| `src/pdf.ts` | **Screenplay PDF writer**, hand-rolled — affordable only because a screenplay is set entirely in **Courier**, one of PDF's 14 standard fonts: nothing to embed, monospaced at 0.6 em so no glyph metrics, every element left-aligned at a fixed indent. That's a few hundred lines instead of a megabyte of dependency. `renderScreenplayPdf` returns **bytes** (the document is assembled as Latin-1 and converted once — building it as a JS string and UTF-8 encoding it would shift every xref offset and produce a file viewers reject). Real typeset geometry: US Letter, 1in margins + 1.5in left, 12pt/12pt leading, per-element indents, word wrap, widow control (a character cue never separates from its dialogue), title page, and page numbers from page 2. **`pdfPages` is the single pagination source** — the preview renders from it too, so what's on screen and what exports agree page for page (the parser's `LINES_PER_PAGE` estimate drives only the cheap live outline). `layoutPages` walks `parsed.elements` directly rather than `paginate()` (which drops `page-break` entirely for the soft pagination) so a `===` line **forces a real page break** here — the one place it has to, or the syntax would do nothing in the file actually exported. A scene heading's production number (`#7#`, `element.sceneNumber`) is laid out as its own line at the **right margin**, never appended into the wrapped heading text. `plainText()` also runs `stripAnnotationMarkers` (fountain.ts) before its own emphasis-mark stripping — the single choke point for comment/alt-text markers on the PDF path specifically, fully independent of the HTML-preview stripping in script-view.tsx/entity-view.tsx |
| `src/fountain.ts` | **Fountain parser** — dependency-free and side-effect-free, so the grammar is testable on its own (everything that touches the vault lives in the view). Title page (`splitTitlePage`/`renderTitlePage` — models Fountain's own keys, preserves unknown ones and their order, so a rewrite never drops what another tool wrote), element tokenizer (scene headings, action, character/dialogue/parenthetical, transitions, sections, synopses, centered, lyrics, page breaks, boneyard, notes), `parseSceneHeading`/`renderSceneHeading`, and **derived pagination** (`LINES_PER_PAGE` 55 + per-element render widths at 12pt Courier). Scene page ranges are computed on every parse and **never stored**, which is what makes a later scene shift by itself when an earlier one grows. Scene ids: `ensureSceneIds` (additive + idempotent — only ever appends), `readLoomId`, `stripLoomIds` (**export only**). The rules easiest to get wrong, all handled: a scene heading needs a blank line before it; a CHARACTER cue is uppercase with a blank line before **and a non-blank line after** (that trailing condition is the only thing separating `SARAH` from `CUT TO:`); the time-of-day split is on the LAST ` - ` so `SAINT-GERMAIN CAFE - NIGHT` works; `INT` must end the word so `INTERIOR` isn't a heading; `#7#` sits at the END of the heading while a leading `.` is the *forced heading* marker. `FountainElement.sceneNumber` holds a scene heading's production number as its OWN field, stripped out of `text` — every renderer positions it separately (right margin) rather than leaving it inline. Consecutive dialogue lines within one cue block (no blank line between, no parenthetical) **merge into a single `dialogue` element** (`\n`-joined) per the Fountain spec — the parser used to emit one element per physical line, which rendered a paragraph gap between lines of the same speech. `reattachSectionIds` mirrors `reattachSceneIds` for top-level sections (chapters) — the same heuristic recovery for an export → edit elsewhere → reimport round trip, since that strips section ids too, not just scene ids. `splitLocationSub`/`joinLocationSub` split/compose a scene heading's location text into a main location and an optional sublocation (`"CAFE - COUNTER"` ↔ `{main: "CAFE", sub: "COUNTER"}`), splitting on the FIRST ` - ` (mirroring the time-of-day split's LAST-`-` convention) — used by both the Scene page's modular heading editor and `syncScenes`'s location matching. `setSceneHeadingParts` rewrites a scene heading's INT./EXT., location or time-of-day, reading the CURRENT raw line for the production number and loom id so neither is ever lost or duplicated. `moveSceneBefore` relocates a scene's block to sit immediately before another scene, wherever that scene is — used by the Scene page's cross-chapter move. **`reorderScenesInSection`** is the Chapter page's own drag-reorder primitive: rather than reasoning about a single "insert before its new neighbor" move (which got demonstrably fragile on a big jump — dragging the 14th scene of 14 to the front once left only 7 visible), it captures every scene's block in the section UP FRONT, removes the whole contiguous range in one splice bounded to the section (never reaching into the next chapter — the LAST scene's raw `endLine` is extended by the parser to whatever scene-heading comes next in the WHOLE file, chapter boundary or not, so the removal end is capped at the next top-level section's line, not trusted from `endLine` directly), then reinserts every block in the exact requested order. Verified against last→first/first→last/reversed/middle→front and a trailing second-chapter case via a standalone Node harness (fountain.ts has zero Obsidian dependencies, so `node file.ts` runs it directly — Node 22+'s native TS stripping handles this codebase's syntax with no build step). `renumberScenes` keeps an EXISTING `#N#` production-numbering scheme sequential after a move (screenwriting convention normally LOCKS these, but the app's drag actions physically relocate the number along with the block, so a reorder without renumbering would leave a stale number on the wrong scene); scenes with no number are never given one. `renameSectionTitle` rewrites a `#` section's title text in place (level + hidden loom id preserved) — what the Chapter page's Title field writes through, since "the script owns names" is about not authoring a rival copy of the text, not about that field being read-only. Both `renumberScenes` and any structural rewrite from the Chapter/Scene pages funnel through `editScriptAndSync` (script-view.tsx), which also re-runs `syncScenes` immediately — necessary because `syncScenes`'s own chapter-matching block only ever updated a renamed chapter's `loomName` frontmatter, never its FILE, so the managed name and the actual file silently disagreed the moment a title changed; fixed alongside making the title editable. `renderInline` swaps a backslash-escaped `\*`/`\_`/`\\` for a Private Use Area placeholder before the emphasis regexes run and restores it as the literal character afterward — without this, `Colour\_DP-01` (a real screenwriter escaping their own underscore) printed the backslash itself instead of being consumed by the escape; `pdf.ts`'s `plainText` mirrors the same fix for the PDF/print path. **Orphan prevention**: `ORPHAN_WORDS` (articles, one-letter words, short prepositions/conjunctions) + `findOrphanPairs` (returns every `<glue word> <next word>` span, pure — no text mutated) + `preventOrphans` (the same matching, but glues with a real non-breaking space) are the ONE shared word list/matcher behind two different glue mechanisms: Pages-preview HTML (both the main Script view and the Scene page's) calls `preventOrphans` before `renderInline` since it's throwaway generated markup, while `fountain-field.tsx`'s live editor calls `findOrphanPairs` and marks the span `white-space: nowrap` instead, since it must never alter the actual document text. Not yet applied to the real PDF export — `pdf.ts` wraps lines itself from character-width math rather than letting a browser wrap HTML, so fixing it there needs the rule taught to that wrap loop directly, not either glue mechanism here. **Inline entity links** (`@[Name|Display]`, bracket-delimited rather than a bare `@Name` since a name can contain spaces/punctuation with no other safe terminator): `findEntityLinks` (position-preserving, feeds both the live-editor decoration pass and `syncScenes`'s scene-entity derivation) and `stripEntityLinksForDisplay` (collapses to `Display` or `Name` — export/render only, wired into every Pages-preview/`.fountain`/PDF surface, never the live document). The `@[` collision with Fountain's own forced-character-cue convention (`@JOHN` at a blank-gated line start) is guarded one line: `forcedCharacter` requires the character after `@` NOT be `[`. **Narrative branching**: `= branch: <id>` synopsis line directly beneath a section heading (no blank line) tags it as one sibling in that choice-point group (`ParsedSection.branchGroup`); `ensureSceneIds` now ids branch-tagged sections at ANY depth, not just level-1 chapters. `ParsedScene.branchLoomId` is the nearest enclosing branch section's id, computed via `sectionStack` (which now also closes any open branch frame the moment a scene heading appears — a branch holds prose, never a further scene of its own, which is what stops a scene written after a resolved choice point from staying misattributed to the last branch). `nextTopSectionLine` extracts the "cap at the next top-level section, or file end" bound duplicated across `moveSceneToSection`/`reorderScenesInSection`/`chapterScriptText` into one place. `applyBranchLabels` mirrors `applyDisplayTitles` for branches — a printed `>**Title**<` marker kept in sync under each branch-tagged section on every commit, auto-derived from the section's own heading text since a branch has no backing note to source a title from. **`renumberScenes` now cascades**: once ANY scene carries a `#N#`, every scene from the document's start through the last currently-numbered one joins the sequence (renumbered 1..N), so a scene typed in fresh before today's `#1#` becomes the new `#1#` and everything after cascades, rather than only resyncing scenes that already had a number. **`reorderTopSections`** is `reorderScenesInSection` one level up — the Script view's own Chapters panel drag-reorder: each top-level section's WHOLE block (its `#` line through everything up to the next one, scenes and nested structure included) is captured up front, the full `[first chapter, last chapter)` span is spliced out in one bounded removal (via `nextTopSectionLine`), then every block reinserts in the requested order; only sections already carrying a loom id are touched, and anything before the first chapter is left untouched since `insertAt` starts there. **`allLoomIds`/`freshSceneId`** are the shared "collect every id already in the script, then roll a fresh one against it" pair — used by `ensureSceneIds`, `appendChapter`, `appendPageBreak` and `appendScene` alike, rather than each reimplementing the collision check (widens `appendChapter`'s/`appendScene`'s own checks to also cover page-break ids, strictly safer). **`trimTrailingBlankLines`** is the shared "drop trailing blank lines off a captured block" step used by `moveSceneToSection`/`moveSceneBefore`/`reorderScenesInSection`/`reorderBranchGroup`/`rebuildTopLevel` — each still re-inserts its own way (leading blank line or not), just sharing the trim. **`appendChapter`** appends a new `# <title> [[loom:…]]` section (with a fresh, collision-checked id) to the very end of the document — what the Outline panel's "+ New chapter" toolbar button writes through instead of creating a bare Chapter note, so the new chapter is born WITH a script anchor and `syncScenes` picks it up on the next commit exactly like a hand-typed `# Chapter` line, rather than existing as an orphan from the moment it's created. **`appendScene`** is the same idea one level down — appends `INT. <LOCATION> - DAY [[loom:…]]` to the very end of the document; since a chapter's content is just "everything up to the next `#` line or EOF" (`nextTopSectionLine`), this needs no target chapter — it lands inside whichever chapter is LAST (or chapterless, same as typing one in by hand, if there's no chapter yet). Both are now also the write-half of `CreateEntityModal`'s scene/chapter creation (project.ts) — a scene picks its chapter explicitly there, so that path follows `appendScene` with `moveSceneToSection` + `setSceneHeadingParts` rather than trusting "whichever chapter is last". **`removeChapter`** mirrors `removeScene` one level up — deletes a top-level section's `#` line AND everything beneath it (bounded by `nextTopSectionLine`, same as `replaceChapterBody`), the whole point being that a Chapter note's own delete action (see `deleteScriptEntity`, script-view.tsx) can take its script block with it in one call, cascading onto every scene heading that block held. **Chapter-boundary page breaks** (`ParsedScript.pageBreaks`, `ParsedPageBreak`): a `===` line is promoted to its own Outline entry ONLY when the very next element (`elements` already skips blanks) is a level-1 chapter heading or EOF — one between two scenes, mid-scene, or right after a chapter heading before its first scene stays exactly where it was typed, plain content, never touched. This is purely positional, computed fresh on every `parseFountain` regardless of whether an id is present yet, which is what lets `nextTopSectionLine` (now stopping at a qualifying page break too, not just the next section) correctly exclude a trailing one from the PRECEDING chapter's own content — the bug this whole feature exists to fix: a page break meant to start the NEXT chapter on a fresh page used to get swept into the LAST scene of the chapter before it, and reordering that scene would drag the break along with it. `ensureSceneIds` assigns a qualifying page break its id the same additive way it does scenes/chapters (never an unqualifying one). `topLevelEntries`/`reorderTopLevelEntries` treat the WHOLE top-level sequence — chapters (their entire block, scenes included) and page breaks — as one reorderable list with a shared low-level splice-rebuild (`rebuildTopLevel`); the Script view's Outline drags this directly. `reorderTopSections` (the Chapter creation modal's own chapters-only position picker) is layered on top of the same rebuild but NEVER drops or strands an existing page break: each one stays attached to whichever chapter immediately follows it in the CURRENT document (a page break's whole point is "start the NEXT chapter fresh", so that's preserved even as chapters move around it), a trailing one with nothing after it stays at the very end. `appendPageBreak`/`removePageBreak` mirror `appendChapter`/`removeChapter` one concept over. **`sceneEndLine(parsed, scene)`** caps `ParsedScene.endLine` at `nextTopSectionLine` and is now mandatory reading for a scene's own span — `endLine` alone extends to whatever scene heading comes next in the WHOLE file, chapter boundary or not (documented, intentional, for callers that already re-cap it themselves), but several places were still trusting it raw: `removeScene`, `moveSceneToSection`, `moveSceneBefore`, `replaceSceneBody`, `sceneAtLine`, `sceneScriptText`/`syncScenes`'s `@[...]`-mention slice (script-view.tsx), the Script view's `scenePages`, and the Scene page's own mini nav bound (`entity-view.tsx`) — every one of them could read, overwrite, or physically relocate the FOLLOWING chapter's heading and first scene when operating on a chapter's own LAST scene. Always latent, but page breaks made it visible (a trailing `===` was the first thing that "leaked" in). **Annotation markers** (comments + alternative text, `[[loom-comment:<id>]]`…`[[/loom-comment:<id>]]` / `[[loom-alt:<id>]]`…`[[/loom-alt:<id>]]`): paired siblings of `[[loom:<id>]]` — same non-exporting Fountain Note syntax, but wrapping a RANGE instead of tagging one line's end. Position is never stored: the marker pair's location IS wherever the user's edits have left it, which is also what makes garbage collection free — deleting the whole wrapped span (both markers) removes them in the same ordinary edit, no special-case code. `findAnnotationSpans` (position-preserving like `findEntityLinks`, always called with the FULL text) pairs every open with the next matching close; `findStrayAnnotationMarkers`/`cleanAnnotationMarkers` are the subtractive counterpart to `ensureSceneIds` — they find and strip a LONE surviving marker (only one half of a pair got deleted, e.g. a partial backspace), the one case that isn't self-cleaning; `liveAnnotationIds` mirrors `liveSceneIds`/`liveChapterIds` for the sidecar-pruning GC pass (`runCommit`/`editScriptAndSync`, script-view.tsx). `stripAnnotationMarkers` is the export/render-only strip (same contract as `stripLoomIds`/`stripEntityLinksForDisplay`, wired into every live render/export call site EXCEPT `PagesPreviewBody` — see next) — because cycling alt-text is a real document edit that replaces the wrapped text in place (fountain-field.tsx), stripping the two marker tokens and leaving the wrapped content untouched already IS full resolution, no separate "pick the active option" step needed. **`wrapAnnotationMarkersForDisplay`** is `stripAnnotationMarkers`'s render-only sibling for the interactive Pages preview specifically: a BALANCED marker pair found in the given text (`ANNOTATION_PAIR_RE`, a backreferenced regex so nested spans of different ids each self-pair correctly) becomes a real `<span class="loom-sp-annotation-span-…">…</span>` wrapping its content instead of vanishing outright, so the preview can box it with the same dashed UNDERLINE the live CM6 editor draws (fountain-field.tsx's own content-mark decoration) — including the same persistent "unresolved comment" tint, via a THIRD parameter, `unresolvedCommentIds: Set<string>` (comment ids still needing attention; a plain `Set`, not `Record<string, CommentEntry[]>`, so this file never has to import a type from script-notes.ts, which pulls in Obsidian — the caller, `PagesPreviewBody` in script-view.tsx, computes it once from its own `comments` prop); an unbalanced marker (the span crosses an ELEMENT boundary — rare, since a dialogue block's several physical lines already merge into one element) has nothing to safely pair against in a single element's own text and is just stripped, same as before. Must run AFTER `renderInline`, not before — `renderInline` HTML-escapes the whole string before applying `**bold**`/`_underline_`, and injecting real `<span>` tags before that would escape them into literal text; the marker tokens themselves survive `escapeHtml` untouched (it only escapes `&`/`<`/`>`/`"`) and `preventOrphans`'s space-pair regex can't match across the token's own bracket/hyphen/colon characters, so leaving them in place through both passes and wrapping LAST (`PagesPreviewBody` in script-view.tsx) is safe. The comment/alt-text BODY data (text, resolved state, options list, active index) lives in a separate project-level JSON sidecar (`src/views/script-notes.ts`), never here and never on a Scene/Chapter note's frontmatter — see that file's own entry and the "Script comments & alternative text" architectural-decisions bullet below for why. **A real parser bug this feature would otherwise introduce, now fixed**: every classification test in the main tokenizer loop (`line.startsWith(...)`, `scenePrefixOf`, `looksLikeCharacter`/`looksLikeTransition`'s uppercase check) originally read the raw trimmed `line` — a comment/alt-text marker opening at a line's very start (commenting a whole scene heading or character cue is ordinary) pushed the real content out of position and silently misclassified the line as plain action text. Fixed by computing `cls` (`line` with every marker token stripped EXACTLY, no whitespace swallowed — a marker can sit mid-sentence, so eating adjacent whitespace would corrupt real spacing) once per line and using it for every classification/extraction decision in that loop, including the dialogue-block's own parenthetical check (`blockCls`); `parseSceneHeading` strips markers internally too (first thing it does, before reading the loom id), so every one of its several existing call sites — which read the RAW line directly — gets the fix for free without being touched individually |

Ids are written on load and on blur, never mid-typing (rewriting the textarea's value would yank the caret). Characters and locations the script names are **created automatically** (`ensureNamed`), matched by name so an existing entity is referenced rather than duplicated — its page, description and relationships untouched; location matching is **sublocation-aware** (`resolveSceneLocation` + `splitLocationSub`) — a heading's location text splits into a main location (matched/created among TOP-LEVEL locations only) and an optional sublocation (matched/created among that main's children), and `sceneLocation` links to whichever is more specific. It shows the location's **connected entities** (`focusNeighborhood` in `mini-graph.tsx` — focus + `getConnections` + one event hop, so sessions come in via events; returns records + undirected edges, no `computeGraphLayout`) in a **maps-specific vertical hierarchy** (`focusLayerOf`, top→bottom: **region straight above** → focus + other main locations → sublocations → items → quests → characters → factions → events → sessions), focus pinned at the node with other mains fanned around it, and a **checker vertical stagger** per row (`FG_STAGGER_Y`) applied only when labels would overlap. **Its connections follow the main graph's edge grammar** (not a bespoke elbow): cross-row edges are routed `fan`s — diagonal exit → vertical trunk lane → optional horizontal run in the band above the target row → diagonal entry fanned across the target's side — and same-row pairs are `rowU`s, both drawn through the shared `edgePoints`/`roundedPath`. Parallel lines hold a **minimum distance**: trunks whose row spans overlap are swept apart by `FG_LANE_GAP`, horizontal runs and U lanes get their own y-lanes from `laneIndices` (greedy interval coloring), band heights grow to fit however many lanes a row needs, and a multi-row trunk steps clear of the nodes it passes (`FG_TRUNK_CLEAR`). The whole layout is computed in **unit space** (`FG_*` constants, one unit = the regular node radius) and multiplied by the page's **element scale** at render, so it's proportional to the map it grows out of. **There is no focus graph in node view** — the map already is a node graph there: a node click in node view only selects, and zooming out into node view retracts an open graph (which is also why the layer takes `scale`, not `nodeUnit` — a retraction across the squish crossfade would balloon). On open the nodes **grow out of the location like a web** (a local rAF `prog`, per-layer stagger, `lerp(nodeWorld, target, nodeProg)` + radius `* nodeProg`); **closing plays the reverse** (retract) animation — the graph stays mounted via `focusClosing` until `prog` eases back to 0, then `onClosed` unmounts. `pointer-events:none` except nodes; double-click a connected node opens it, **click the focus node (or Esc) hides**. (`buildFocusLayout` still exists for the main-graph `MiniGraph`.) **Region hulls morph instead of snapping** (`hullState`/`hullTargets` refs + `resampleRing`/`ringCentroid`): each cluster's hull is resampled to a fixed ring, matched to the previous frame's rings by nearest centroid (biggest cluster claims its key first), and an rAF eases each `display` ring toward its target while in node view — so a cluster split retracts the surviving border and grows a new one out of the split-off centroid ("rip out + hug back"). A vanishing/merged cluster **fades (`alpha`) and shrinks its pad** as it collapses so it disappears behind the node instead of leaving a fixed circle; a constant-screen pad (× alpha) is applied to the eased ring at render. The **camera is remembered per map page** (`settings.mapCameras` keyed `${root}::${pageId}`, `restoreCamera(pageId, scale)` on switch/load, previous page's camera snapshotted synchronously before a switch); the **find-a-location search eases** the camera to its pick rather than snapping (`flyTo`). A **waypoints mode was deliberately dropped**: the focus graph covers "what is this place connected to" and the main graph already lays out every connection, so a third half-graph earned nothing. **`newZone()`** builds the shared 9-field `MapZone` default shape used by `finishDraft`/`finishRoad`/`finishRect` — check it before hand-rolling another zone object literal. **`ZonePinList`** is the shared component behind `ZonePanel`'s sublocations/doors/items palette popovers (search + 2-column header + scrollable draggable rows) — parameterized per pin kind rather than three near-identical copies; reuse it for any future zone-menu list popover of the same shape. ## Key architectural decisions

- **Project kinds** (`src/project-kind.ts`): a project is a **Player**, **Game Master** or
  **Writer** project (`kind` in its .loom config, picked at setup, switchable in settings).
  A kind is a *config layer over one shared data model, never a fork* — it decides which
  entity types the project holds (`typesFor`) and which optional behaviour is on
  (`KindFeatures`). Chapter/Scene are their **own entity types**, not renamed
  Session/Event: they carry genuinely different fields (a session has a date and
  attendance; a chapter has a manual order and an exported display title). What keeps
  that from doubling every code path is **structural roles**: the chronological anchor
  (Session / Chapter) and the beat that stacks beneath it (Event / Scene). Shared code —
  `columns.ts`, `graph/layout.ts`, the timeline strip, the list and entity-page shells —
  asks `projectRoleType(config, 'anchor')` or `roleOf(record.type)` and never names a
  type, so one implementation serves both chronologies. `roleOf` is kind-independent (a
  type has exactly one role globally), which lets record-only code branch without
  resolving a project. Genuinely divergent bits gate on features instead:
  `kindFeatures.attendance` hides the attendance block in a writer project,
  `features().group` hides the virtual Group (it's the party — built on the PC tag), and
  `anchorOrder` switches anchor sorting from date to `loomSeq`. **The graph's `NodeKind`
  follows the same names** (`anchor` / `beat` / `global`) — it is a layout row, not an
  entity type. Switching a project's kind moves no notes; the unused entity folders just
  stop being listed. GM planning (`FM.eventKind` = planned/locked/improvised,
  `FM.happened`, `FM.npcLines`) is still an indexed placeholder — fields read, UI not built.
- **The script is a `.fountain` file, not a note** (`src/fountain.ts`, `src/views/script-view.tsx`).
  Two reasons it can't be markdown: Fountain's note syntax **is** `[[…]]`, so Obsidian would
  index every non-exporting script note as a wikilink and fill the graph with them; and its
  own extension round-trips byte-for-byte with Better Fountain / Highland / Fade In, which is
  what makes "Open in external app" honest rather than a lossy export. Accepted cost: core
  search only indexes `.md`, so finding script text needs our own index. It lives at
  `<root>/<Project>.fountain`, scaffolded for writer projects and created on demand from the
  rail/home for a project switched to Writer later. **Scene identity is a hidden
  `[[loom:<id>]]` Fountain note in the heading** — non-exporting by spec, hidden by our
  editor, and it survives a rename-and-move that any text heuristic would lose (silently
  detaching the scene's relationships and notes). **Strip those ids on export only, never on
  "Open in external app"**: export makes a copy, open-in-external hands over the live file an
  editor writes back to. That leaves one lossy path — export stripped → edit externally →
  import back — and heuristic matching belongs there and only there, as recovery. A scene's **chapter is the top-level `#` section** it sits under (`FM.sceneChapter`, a visible
  link, which is also what stacks it under its chapter in the graph); chapters are created and
  ordered from the sections automatically because the script owns them. **Direction of truth
  is split and deliberate**: the SCRIPT owns names (a `#` section renames its Chapter note, a
  scene heading renames its Scene note — so both name fields are read-only on the page), while
  the NOTE owns `loomDisplayTitle`, which `applyDisplayTitles` writes back into the script as
  the centered-bold line under its section (Fountain sections never export, so a title that
  must reach the PDF has to be emitted separately). Splitting it this way avoids a two-way
  merge with no base to compare against. A writer project's Chapter page lists its scenes from
  those `sceneChapter` links rather than from the session-note hub, and a Scene page shows a
  read-only window onto its stretch of the script (`sceneScriptText`) instead of authoring
  notes of its own — the .fountain file stays the single home of the writing. A scene's
  `INT./EXT.` and time of day live on the SCENE (`FM.sceneIntExt`/`FM.sceneTime`), not the
  location: the same house is INT. in one scene and EXT. in the next. **The Scene page's
  heading IS editable, just not as free text**: a modular INT./EXT. + Location + Sublocation +
  Time field group (`setSceneHeadingParts`, `splitLocationSub`/`joinLocationSub`) writes the
  heading's structured parts back into the script — the direction-of-truth split above is about
  the note never authoring a rival copy of the heading TEXT, not about the fields behind it
  being read-only. Location/Sublocation are bound to the actual linked location entities: typing
  over an already-linked one's name renames that entity everywhere (same as any other Name
  field), a name matching nothing creates a location/sublocation, and changing the main location
  while a sublocation stays linked reparents that same sublocation rather than creating a
  second one. **Creation and deletion are both single-surfaced**: every "New scene"/"New chapter"
  entry point (entity list, Script view toolbar, a session row's context menu) opens the same
  `CreateEntityModal` branch (`project.ts`), which writes the script anchor FIRST and only then
  stamps the note — so nothing made through the app is ever born orphaned the way a bare
  entity-note creation would be. Deletion is the mirror: trashing a Scene/Chapter note always
  removes its backing block from the script in the same action (`deleteScriptEntity`,
  script-view.tsx), from every delete entry point (entity page, both list-view.tsx delete paths) —
  deleting a Chapter cascades onto every Scene note it held, since their headings just left with it.
- **Storage**: markdown files + YAML frontmatter are the source of truth; one entity per
  `.md` file, native `[[wikilinks]]` so Obsidian's own backlinks keep working.
- **Projects are .loom files**: any folder holding a `<Name>.loom` file (JSON: per-project
  config — date format, custom calendar) is a project. The .loom file is the visible
  file-explorer entry point (registered extension, like .canvas/.base) and opens the
  React home view. Multiple projects per vault; views carry the project root in state.
- **Index cache**: `LoomIndexer` discovers projects, builds in-memory records from
  `metadataCache` frontmatter, updates incrementally on file events, and persists a
  debug/cold-start JSON snapshot. Indexing has no rendering concerns; views never re-scan files.
- **Link resolution is lazy**: records store unresolved linkpaths; resolution to files
  happens at query time via `metadataCache.getFirstLinkpathDest`, so renames/creations
  can't leave stale resolved paths.
- **Views**: all custom UI is React 18 mounted inside `ItemView`/`FileView` subclasses
  (`LoomReactView` / `LoomFileReactView` bases). Loom-internal clicks open the structured
  entity page view; opening the same .md from the file explorer gives the raw editor.
- **Names**: the user-entered name lives in `loomName` frontmatter (source of truth
  for display); every file name is managed — `<Project> <Type label> <name>`,
  sessions `<Project> Session <date>` (no loomName; they display their date),
  **sublocations `<Project> Sublocation of <parent name> — <name>`** (embeds the
  parent's name so same-named places under different parents stay distinct; setting/
  clearing `parentLocation` renames the file, migration reconciles the whole tree by
  precomputing parent names). Editing the name renames the file (Obsidian updates
  links); `aliases` gets the display name so native `[[…]]` autocomplete finds notes
  by it. Plugin-written links always target the file basename (`linkTargetOf`); every
  picker searches/labels by display name — sublocations label as `Tavern, City A`
  (`locationLabel` in common.tsx). A startup migration (`LoomIndexer.migrateFiles`)
  converts old files.
- **Frontmatter keys are all loom-prefixed** (`FM` registry in types.ts: `loomType`,
  `loomName`, `loomDate`, `loomRelationships`, `loomSessionNotes`, `loomMembers`, …).
  Reads fall back to legacy un-prefixed spellings; writes go through `src/fm.ts`
  helpers which clean legacy keys up; the startup migration rewrites old notes.
  Nested keys inside list entries stay unprefixed; `aliases` is deliberately native.
- **Regions** (`region` entity type): a grouping layer *above* main locations — a way
  to gather locations under a territory without turning them into sublocations. A location
  carries a dedicated `region` field (`FM.region`, "Part of region" on every location page
  right after "Sublocation of"; "Not specified" when empty) that emits a typed `region`
  connection (like `parentLocation`→`sublocation`); `regionOrder` (hidden links) orders a
  region's members. The **region page** reuses the location page shell but shows a
  **Locations** section (its member locations — add existing / create new / remove) instead
  of Sublocations, and **inherits events** from its members via the same `places`
  ancestor-propagation, one layer up (`placeInThisRegion`: a place counts if it or any
  ancestor is a member). Region color is **not configurable** — always a darker shade of the
  location color (`syncRegionColor`/`darkenHex`, run in `mergeSettings` and on any
  location-color change); regions reuse `EntityChip`. Regions are in `GLOBAL_TYPES` (graph
  nodes) but **not** map nodes and are never offered as a map zone's location. The location
  **list groups locations under their Region** (main location under its region header,
  sublocations still under their parent; synthetic "Unspecified Region" for none; flat until
  a region is in use — `UNSPEC_REGION` in list-view). **On the map (node view only)** a region
  draws an auto-computed **padded convex hull** around each *cluster* of its locations' **zones**
  (the actual land areas, hulling every zone vertex — not the collapsed node points): the region's
  zones are clustered by proximity (union-find, threshold = 2.5× the map's median
  nearest-neighbour spacing) so far-apart members wrap **separately** — one hull per cluster,
  labelled, double-click opens the region page (`regionClusters` + `regionHull`/`convexHull` in
  map-view; color = darker location, fades in with the squish).
- **Events section (entity pages)**: character/item/faction/location/**quest** pages
  show the events they take part in instead of their own session notes. A note's
  `involved` list surfaces the event on each involved entity's page (quests included —
  a quest is `involved` in the events that advance it; **locations may be involved too**
  — a place discussed/featured in the event, distinct from where it happened); a note's
  `places` list (the event's per-note location, stored on the event, replacing the old
  event-level `location` relationship) surfaces it on that location **and every ancestor
  location** (city ⊇ tavern ⊇ secret room) — the location page's Events section reads
  `places` only, so an involved-but-not-placed location isn't listed there. Involve
  pickers (page editor + hub rows + create modal) offer every non-session/non-event
  type, locations included. Removing the page's own entity from a note warns first
  ("… this event won't be displayed here anymore"). Only **event** pages keep an
  editable own-`sessionNotes` section (quests no longer author their own notes — the
  session-page hub is labelled **Events** and never shows a Quests subsection). Adding
  an event is a `SearchableSelect`: picking an existing event involves this page's
  entity in that event's first note (`places` for a location page, else `involved`),
  and "+ Create new event" opens the modal pre-linking the page's entity
  (`defaultInvolved` / `defaultPlace`). Creating a quest from an event note's Involve
  search prefills the quest's "Received in session" with that note's session
  (`CreateEntityModal` `receivedSession` — sets `questReceived` without pinning a note).
- **Quest page specifics**: the **Reward** field is a `MarkdownField` (links, multiple
  lines — a reward `[[item]]` connects in the graph as a plain link). An **Objectives**
  section (after Tags, `loomObjectives` frontmatter: ordered `{ name, finishedOn? }`
  entries) splits into **Active** (no `finishedOn`) and **Resolved** (a `finishedOn`
  session, picked like "Received in session"); "+ Add objective" appends a row, active
  rows drag-reorder (a drop rewrites the stored list as reordered-actives then the
  resolved). `finishedOn` links are hidden (no graph edge — `loomobjectives` in
  `HIDDEN_LINK_KEYS`).
- **Session-page Quests section**: three collapsible groups computed as of the session's
  date — **Active**, **Resolved this session** (`questOutcomeSession` is this session),
  **Resolved previously** (resolved in an earlier session, capped by
  `settings.sessionResolvedQuests` — 3/6/9/12/All, default 6, newest by outcome date;
  the count reads "N of total" when capped). Only Active reorders (`loomSeq`).
- **Section order / Events last**: the **Events** hub is big, so it is the last
  content section on every entity page — only **Relationships** and **Connected
  entities** follow it. It's extracted into one `eventsSection` node rendered in a
  SINGLE unconditional spot at the bottom (null on pages that don't show events, e.g.
  event/session), so the page-specific sections above it (item-holder Characters/
  Locations on item pages; Factions → Items → Sublocations on location pages) all come
  first. Per-page differences that can't be a single global order live inline above
  Notes: a location page is Notes → Factions → Items → Sublocations → Events, while a
  character page puts its Faction(s) membership section and the shared `itemsSection`
  ABOVE Notes (Items directly under Faction(s)). The Factions section's members hang
  off a vertical nesting rail (shared `loom-event-nest`) under each faction chip.
- **Items section (character/location pages)**: an ordered `loomItems`
  frontmatter list of item links on the character/location. **A location also has an "Items in
  sublocations" subsection** (`inheritedGroups`) — every descendant sublocation's
  items, **grouped under the sublocation** on a nesting rail (Factions-section layout,
  alphabetical, read-only chips); persistent (shown even if the same item is also on
  this location directly). Each row edits the item
  entity in place (name renames the item file, description writes its `loomDescription`);
  drag-reordering rewrites the page's `loomItems` order (per-page). Adding searches
  existing items (+ "Create new item"). Each row's `<` drawer holds Delete (trashes the
  item note) + Remove (just unlinks it from this page); on a character page a `layers-2`
  button (left of Delete) makes a character-specific copy. The links are visible
  (non-hidden) so items also connect in the graph.
- **Item page reverse sections**: an item page shows **Characters** (after Notes,
  above Events) and **Locations** (after Characters) — the holders that carry this item via their
  `loomItems`. Chips (persistent entities, not editable), an "Add to character/location…"
  search that writes the item into the picked holder's `loomItems`, and a remove ✕ that
  unlinks it. Direct reverse query only (a holder that swapped in a character-specific
  copy no longer credits the original).
- **Character-specific item copies**: the `layers-2` button on a character-page item row
  (standalone next to the row's open arrow, not in the delete/remove drawer; tooltip
  "Replace with a character specific copy of this item") creates a copy item note
  `<Project> Item <original> — <character>`, replaces the original in that character's
  `loomItems` with it, and opens it. The copy carries `loomItemOrigin` (visible link →
  graph edge to the original) + `loomItemOwner` (hidden link — the character already
  connects via `loomItems`); its `loomName`/`aliases` are the `<original> [<character>]`
  label (each original alias also suffixed `[character]`), so pickers and native `[[…]]`
  search show it that way. **The copy note is written with a raw frontmatter string, not
  `processFrontMatter`, so aliases stay quoted (`["Excalibur [Arthur]"]`) — an unquoted
  `[…]` suffix reads as a YAML flow sequence and breaks Obsidian's alias mechanic.**
  `managedEntityFileName` takes an `ownerName` for the `— <owner>` file name; the startup
  migration reconciles copy names from the resolved original + owner. In a character's
  Items row a copy shows read-only (no rename, no re-copy). The entity list nests copies
  under their original (same machinery as sublocations, via `itemOrigin`) with the owner
  as an `EntityChip`. A copy's page has no editable name (original chip + owner chip
  instead); its Description shows the original until edited, at which point the field
  becomes **Alternative description** (writes the copy's own `loomDescription`) with a
  collapsed **Original description** spoiler (read-only `MarkdownField`, `readOnly` prop);
  clearing the alternative reverts to the original.
- **CreateEntityModal existing-match**: when the searchable Name field (session-page
  event/quest add) matches an existing entity, the primary button flips from "Create" to
  "Add" — submit pins it to the session instead of creating a duplicate.
- **Connections**: typed frontmatter relationships + `sessionNotes` (session-pinned
  note entries `{session, text, involved, places}`; the picked session becomes a
  `session note` connection, `involved`→`involved`, event/quest `places`→`location`) + `parentLocation` on locations (sublocation parent — dedicated field
  with its own page/list/graph UI, never a relationship; typed `sublocation`
  connection) + `members` on factions (member characters, plain links or
  `{ character, role, location }` objects; typed `member` connection; mirrored on
  character pages as an editable "Faction(s)" section — role / faction / optional
  location rows plus "+ Add faction" — writing the faction's file) + plain
  `[[links]]` anywhere in a note (relType `link`), all resolved
  bidirectionally; graph edges undirected. There is no dedicated event→session field
  (`linkedSession` was removed — relationships already cover it; old keys in existing
  notes still connect as plain frontmatter links). Entity tags
  live in `loomTags` (legacy `pluginTags` still read); the tag vocabulary is hardcoded
  (`ENTITY_TAGS` in types.ts), not user-configurable.
- **Virtual "Group" faction**: entity-connecting pickers (Involve… on note rows,
  faction Members, relationship targets, the create-modal's Involved field) offer a
  file-less "Group" entry (`PC_GROUP_NAME`/`PC_GROUP_VALUE`/`pcGroupStub` in types.ts).
  The party at pick time = `LoomIndexer.getGroupMembers`: PC-tagged AND `alive` AND
  `active` (`loomActive`, a PC-page checkbox next to Alive — untick while a character
  is away from the party, re-tick when they rejoin; new picks skip inactive PCs, old
  snapshots keep them). In **involved pickers** the pick writes a `group` snapshot
  list on the note entry (sibling of `involved`; frozen — later deaths don't rewrite
  history) rendered as ONE faction-colored "Group" chip (✕ clears it), while each
  member still connects individually (relType `involved`, individual graph edges).
  In Members/relationship pickers the pick expands to individual entries immediately
  (a relationship draft row becomes one row per member, same type). No entity named
  "Group" ever exists — it never shows in the entity list or graph, the entry hides
  when a type filter excludes characters/factions or nobody's missing, and creating/
  renaming a real faction to "Group" is blocked with a Notice (reserved name). The
  Group also has its own page (`VIEW_GROUP`, `src/views/group-view.tsx`,
  `circle-star` icon): first entry in the nav rail and on the home wheel, laid out
  like a faction page. Its name is editable — stored as `groupName` in the .loom
  config (`groupNameOf` in calendar.ts; '' = the "Group" default, the name is NOT
  reserved for real factions) and used by every picker label, chip, rail/home
  entry. Group chips link to this page. The Group is its own entity color-wise:
  `settings.groupColor` (first "Entities colors" picker, default `#46b5a5`) colors its chips
  (EntityChip + the modal's renderChip special-case the stub's sentinel path),
  home-wheel button, and page header — even though it never appears in the graph.
  Layout: Name, then Members with Alive / Inactive / Dead sub-sections (dead PCs
  pair their chip with the death session's chip), then the Events hub — every
  event/quest where the Group or ANY PC (alive or not, active or not) is on a
  note (snapshot or direct involvement). The hub has a search (event names +
  note texts) and, folded behind a filter icon (accent-lit while active), a
  filter panel: quick-toggle PC chips, an any-entity search with the standard
  type-filter menu (an entry matches when every selected entity is on the note —
  involved, in its group snapshot, or among its places), and a session-month
  filter (year switcher + 3×4 Gregorian month grid, multi-select across years).
  Rows are read-only mirrors of the entity-page event rows — the event NAME is
  the link (no → button) and note text renders through the read-only
  `MarkdownField` (links/bold/bullets). The create modal still accepts
  `defaultGroup` (pre-filled group snapshot).
- **Hidden connections**: links under the `deathSession`, `sublocationOrder`, and
  `itemOwner` (a copy's owning character — already connected via `loomItems`) keys
  never become connections or graph edges. `attendance` is hidden from the generic
  link pass but emits typed `attendance` connections (a ticked PC connects to the
  session). Sessions list attending PCs (`PC` tag); PCs carry `alive`, `active`, and
  `deathSession` — sessions dated after a PC's death session stop offering them.
- **Dates**: `LoomDate` = raw string + packed sortable number + y/m/d + calendar id.
  Sessions always Gregorian; other entities use the project calendar (custom in-game
  months when enabled). Formatting is per-project config, never JS `Date`.
- **Manual order**: events and quests carry a `loomSeq` frontmatter stamp (falling
  back to file ctime). The timeline event bubbles and the session page's session-note
  hub rows (event + quest groups) both sort by it and both drag-reorder by re-stamping
  the whole list, so a reorder in either place shows in the other. (The old
  settings-based `timelineManualOrder` is superseded and unused.)
- **Entity chips**: every entity reference rendered as a tag/pill goes through
  `EntityChip` (`src/views/common.tsx`) — node-colored, clickable name, optional ✕.
  Never hand-roll chip spans; in non-React surfaces (modals) replicate its exact
  markup (`loom-chip loom-session-chip loom-entity-chip` + inline node colors, see
  `CreateEntityModal.renderChip`). Session chips are special-sized in some spots via
  container CSS but always carry the session node color.
- **Inline entity links in the script** (`@[Name|Display]`, `src/fountain.ts`): a
  plugin-specific convention (bracket-delimited, since an entity name can contain
  spaces/punctuation with no other safe bare terminator) that lets a Character,
  Faction, Location, or Item be referenced from ANYWHERE in the script text, not just
  a scene's own heading or CHARACTER cues. `syncScenes` derives `sceneFactions`/
  `sceneItems`/`sceneMentionedLocations` from these per scene (excluding the scene's
  own heading location) and merges any `@[...]`-tagged character into `sceneCast`
  alongside cue-derived ones — resolution is autocomplete-pick only, never
  auto-create, unlike `ensureNamed`'s behavior for scene characters/locations from
  cues/headings. Stripped to plain display text on every export/render path, never on
  the live document, same contract as the `[[loom:<id>]]` scene-identity marker.
- **Quests resolve against Scenes in a Writer project**, the way they resolve against
  Sessions (by date) in a Player/GM one — a Chapter has no date or single sitting of
  its own, a Scene does. `questAnchorRole` flips the valid resolution-target role
  (`'beat'` vs `'anchor'`) and the "Received in"/outcome pickers per project kind
  rather than widening to accept either; a Chapter's own Quest section aggregates
  "resolved this Chapter" from the union of its scenes' resolutions, since a quest
  never resolves directly on a Chapter in this model.
- **Narrative branching** (`= branch: <id>`, `src/fountain.ts`): a synopsis line
  (Fountain's own non-exporting `=` construct) directly beneath a `##`/`###` section
  heading (no blank line) tags it as one sibling in a choice-point group — deliberately
  NOT a new entity type, just a hidden loom id on the section (`ensureSceneIds` now ids
  branch-tagged sections at any depth) plus a Scene's own `sceneBranch` (a raw id, not
  a link — there's no Branch note). A scene heading always closes any currently-open
  branch frame (a branch holds prose, never a scene of its own) — the fix for the
  reported bug where a scene written after a resolved branch stayed misattributed to
  it in both `sectionStack` (fountain.ts, feeding `sectionPath`/`branchLoomId`) and the
  Script view's nav tree (`buildNavTree`, which additionally attaches a branch section
  under the nearest SCENE seen so far — in document order, not just the current stack
  frame, since several branch groups in a row all belong to the same preceding scene —
  rather than the enclosing chapter). `applyBranchLabels` prints a `>**Title**<` marker
  under each branch section on every commit (mirroring `applyDisplayTitles` for
  chapters), auto-derived from the section's own heading text.
- **Script comments & alternative text** (`src/fountain.ts`, `src/views/fountain-field.tsx`,
  `src/views/script-notes.ts`): two creative-process aids on arbitrary selected script
  text, built on the SAME "hidden non-exporting Fountain Note" trick as `[[loom:<id>]]`,
  just extended from tagging one line's end to wrapping a RANGE — `[[loom-comment:<id>]]`
  …`[[/loom-comment:<id>]]` marks a commented span, `[[loom-alt:<id>]]`…`[[/loom-alt:<id>]]`
  marks an alternative-text span whose wrapped content is always whichever option is
  CURRENTLY active (cycling replaces it with a different option's text as a real document
  edit, never additively). **Position is never stored anywhere** — the marker pair's
  location IS wherever the user's edits have left it — which is what makes garbage
  collection free: deleting the whole wrapped span (both markers) removes them in the same
  ordinary edit, no special-case code; only a LONE surviving marker (a partial delete took
  out just one half) needs an explicit sweep (`cleanAnnotationMarkers`, run alongside
  `renumberScenes` in every commit). The comment/alt-text BODY data (text, resolved state,
  an alt-text's option list + active index) lives in a **separate project-level JSON
  sidecar** (`Entities/Script Notes/<Project> Script Notes.json`, modeled on the Maps
  precedent), never in the script itself (no frontmatter to hold it) and never on a
  Scene/Chapter note (a marked range can span a scene boundary or predate any note, and
  `processFrontMatter` rewriting the whole note file on every comment edit is exactly the
  sync-conflict risk this codebase already avoids elsewhere). Fully interactive in **all
  three** places script text renders (main Script view, Scene page, Chapter page) — a
  right-side CM6 gutter in the raw editor plus a right-margin icon in the shared
  `PagesPreviewBody` Pages-preview component, both reading/writing the same sidecar via
  `useScriptNotes`/`mutateScriptNotes`. Search (`ScriptSearchMatch`) merges comment-body and
  alt-text-option hits into the normal text-substring scan, sorted into document order by
  each match's underlying marker position; a comment match auto-opens its popover, an
  alt-text match highlights its icon without changing what's active. Comments/alt-text
  never export — `stripAnnotationMarkers` runs at every render/export boundary alongside
  the existing `stripLoomIds`/`stripEntityLinksForDisplay` strips. A real parser bug this
  feature would otherwise have introduced (a marker opening at a line's very start pushing
  a scene heading or character cue's real content out of position, silently misclassifying
  it as plain action text) is fixed via a marker-stripped `cls` view used only for
  classification, never for the stored element text. **A COMMENT span's coverage is visible and
  adjustable, not just its endpoints**: the CONTENT itself (not just the hidden marker
  tokens) gets a persistent dashed-UNDERLINE mark — like a selection that never clears — on
  both the live CM6 editor (`fountain-field.tsx`'s own `Decoration.mark`) and the Pages
  preview (`wrapAnnotationMarkersForDisplay`, fountain.ts, since that surface builds plain
  HTML strings rather than CM6 decorations); a full box border was tried first and dropped
  for a multi-line span — an inline element's border gets its own top+bottom edge on EVERY
  wrapped line (standard CSS fragmentation behavior), so two lines showed a doubled dash
  right at the wrap. In the editor, small drag handles sit at each edge (`AnnotationHandleWidget`)
  — COMMENTS ONLY: dragging one relocates the marker TOKEN itself to a new position (never
  touches the wrapped prose), guarded against producing a partial overlap with a different
  span (the same invariant the right-click creation menu already enforces). **Alt-text spans
  are deliberately NOT draggable** — an alt-text span's whole point is "this exact stretch of
  text has alternatives," so its coverage stays fixed to whatever was selected at creation,
  never adjustable after the fact, unlike a comment's (which is just marking a passage, not
  tied to specific wording). **A comment thread's resolved state drives a persistent tint,
  not just its icon**: `CommentEntry` gained `resolvedAt` (when `resolved` last flipped true,
  separate from `updatedAt` so a later text edit doesn't change it) and a span is "unresolved"
  (tinted background, needs-attention) whenever ANY reply in its thread isn't resolved yet —
  fully resolved (every reply checked off) drops back to a plain dashed underline, no tint.
  **Alt-text's "active" and "accepted" are two different things**: `AltTextEntry.acceptedIndex`
  (separate from `activeIndex`) marks one option as the FINALIZED choice, `null` while the
  span is still undecided — `AltTextModal`'s "Draft"/"Accept" pills (replacing an old single
  "Use this" button) both make an option the active/displayed text, but only Accept also
  stamps `acceptedIndex`; picking a different Draft explicitly clears it, since choosing a
  different draft means the span is back to "still deciding." Editing an option's wording
  in place, or accepting/drafting a different one, funnels through handlers
  (`handleEditAltOption`/`handleDraftAlt`/`handleAcceptAlt`, script-view.tsx and
  entity-view.tsx) that update the sidecar and — only when the touched option IS the active
  one — push the same text into the live document too, so a later reopen never silently
  reverts an edit. `AltTextModal.onDeleteOption` removes one option outright (behind a
  `ConfirmModal`, disabled when only one option remains) and hands the caller-renumbered
  `{options, activeIndex, acceptedIndex}` back so the modal's own list stays in sync without
  reimplementing that shifting logic itself. The alt-text right-click UI is `AltTextModal`
  (project.ts), a real closeable Obsidian `Modal` — not an anchored popover — specifically
  so every option can be shown in full and EDITED in place (a plain `Menu`/popover can't host
  a multi-line editable textarea per row); it owns its own local list state and re-renders
  itself after each action, needing no React state in the caller to track whether it's open.
  **A Comments/Alternatives browser panel** (two standalone icon toggles next to the main
  Script view's Script/Pages pill, mutually exclusive with each other and the nav panel via
  `openSidePanel`) surfaces what needs attention without scrolling the whole script by hand:
  the Comments panel lists every comment span with at least one unresolved reply (an excerpt
  of the commented text, its unresolved replies nested underneath); the Alternatives panel
  lists every alt-text span with `acceptedIndex === null` — still undecided. Clicking a row
  force-switches to Script mode (`pendingSelectRangeRef`, the same "stash it, apply once
  `FountainField` remounts" pattern `pendingScrollLineRef` already used for the Script/Pages
  scroll sync) and selects the span's full range — a real CM6 selection only makes sense in
  the live editor, unlike the read-only Pages preview. **Also present on the Chapter and Scene
  pages' own embedded Script sections** (entity-view.tsx, each with its own independent
  open/closed state and outside-click-close, mirroring that page's existing nav-panel
  convention rather than the main view's `openSidePanel`), scoped to just that page's own
  excerpt: spans are found via `findAnnotationSpans(chapterDraft)`/`findAnnotationSpans(sceneDraft)`
  — the HEADING-STRIPPED body text, i.e. the EXACT string each section's own `FountainField`
  holds — rather than the raw excerpt (which still has the heading line), so a span's offsets
  already line up with `selectRange` with no line-math conversion needed (unlike the read-only
  nav tree, which is built from the WHOLE document and has to convert absolute lines back to
  excerpt-relative ones).
- **Freemium licensing** (`src/license/`, prep phase — see ROADMAP "Licensing"): one
  project of each kind (player/gm/writer, and any future kind) is free with **every**
  feature available; a license key unlocks unlimited projects, activatable on up to 3
  devices. Gated only at project **creation** (`SetupProjectModal.submit()` in
  `src/project.ts`) — never at opening/using an existing project — which grandfathers
  any vault that already had multiple projects before this shipped, with no migration
  needed. No custom backend: the plan is to call the provider's activate/validate/
  deactivate endpoints directly from the plugin via `requestUrl` (those specific
  endpoints are designed to be called with just the public license key, no secret
  exposure risk), behind a provider-agnostic `LicenseProvider` interface so the concrete
  backend is swappable — `StubLicenseProvider` (in-memory, no account needed) is the
  active provider today, `PolarLicenseProvider` is written but inert pending a live
  Polar.sh account to verify its wire format against. **Per-device state (device id +
  activation) is cached via `App.loadLocalStorage`/`saveLocalStorage`, never
  `Plugin.saveData()`**: `saveData` writes inside the vault folder, which this codebase
  already treats as synced across the user's own machines (see "Playing nicely with
  file sync" in `docs/ARCHITECTURE.md`) — writing device-specific state there would let
  two machines sharing one vault silently share or clobber one "device" record instead
  of representing two. Must not break offline: a cached "paid" verdict keeps unlocking
  unlimited projects for a 30-day grace period (`GRACE_PERIOD_MS`, `src/license/
  grace.ts`) with no successful re-check required, re-verified periodically in the
  background (`main.ts`'s `registerInterval`) and on demand. A provider result
  distinguishes a *definite* rejection (`{ok:false, reason}` — revoke immediately, e.g.
  a refunded key) from *not reaching the server at all* (a thrown error — leave the
  cached verdict alone and let the grace period keep counting down); see `provider.ts`.
  **Open and unresolved, not a settled decision**: whether Obsidian's official community
  plugin directory allows paywalling in-app functionality itself (vs. paywalling a
  backend service the plugin calls) — resolve with Obsidian before any public pricing
  copy ships. Also open: `loadLocalStorage`/`saveLocalStorage` are `@since 1.8.7`, newer
  than this plugin's `minAppVersion` of `1.7.2` — `cache-store.ts` feature-detects and
  falls back to an in-memory, session-only cache on older Obsidian rather than crashing,
  but whether to bump `minAppVersion` instead is still an open product call.

## Constraints

- **No Obsidian 1.13-only APIs** (`setDestructive`, `getSettingDefinitions`, …): 1.13 is
  Catalyst-only early access. `minAppVersion` stays 1.7.2 until 1.13 ships publicly.
  The typings package is 1.13, so a symbol existing in obsidian.d.ts does not mean it's
  safe to call — check when it was introduced.

## Workflow

- `pnpm run build` — typecheck + production bundle; `pnpm run lint` — Obsidian's ESLint
  rules (treat errors as build failures); `pnpm run deploy` — build + copy the three
  release files (`main.js`, `manifest.json`, `styles.css`) into both test vaults:
  `~/Dropbox/Obsidian/Test Vault` and `~/Dropbox/Obsidian/Main vault` (the user's real
  vault — real campaign data lives there, so writes must stay conservative). Deploy at
  every ready-to-test state.
- Releases ship exactly those three files, built by `.github/workflows/release.yml` when
  a GitHub release is created; `main.js` is never committed.

See `ROADMAP.md` for what's built vs. planned and `docs/ARCHITECTURE.md` for the deeper
"why" behind the design.
